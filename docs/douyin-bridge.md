# 平台账号绑定（抖音 / B 站）——可行性结论与映射设计

## 结论

不做在 App 层。App 只同步 DSH 桌面端的会话和状态，刷抖音、看 B 站、回复好友这些动作发生在 DSH 的某个会话里；App 负责让它可配置、可开关、可查看。

原因有三条：
1. 平台侧要真人浏览器登录态、验证码、页面采样，App 里重做一遍等于把整套自动化搬进 Android，且后台保活更难。
2. 会话本来就带工作目录、模型、记忆、插件权限，这些都是「这个人设是谁」的载体；把绑定关系挂在会话上，比挂在手机上一致得多。
3. 桌面端已经有可用实现，重复实现只会分叉行为（回复策略、去重、许可名单各写一遍）。

## 映射模型

一句：**一个平台账号 + 一个好友/群白名单 → 一个 DSH 会话；会话决定人格、工作目录和能做什么。**

```
binding {
  id                     // 绑定 id，UI 显示用
  platform: douyin|bilibili
  account               // 平台稳定身份（不是昵称、不是头像）
  sessionId             // 承载这个身份的 DSH 会话
  workdir               // 这个会话的工作目录（记忆、素材、导出都落这里）
  persona               // 人格卡引用，跟 pocket-harness 现在的 preset 同一套
  allow {
    reply: bool         // 新消息回复
    share: bool         // 观看中主动分享作品卡片
    comment: bool       // 公开评论，默认 false
    autoWatch: bool     // 自主观看，默认 false
  }
  allowlist {
    friends[]           // 平台稳定身份，不用同名/头像猜人
    groups[]
    mentionName         // 群里被 @ 或叫到这个名字才回
  }
  budget { dailyMinutes, dailyRequests }   // 每日额度，可「不限」
}
```

- 好友/群 → 会话是多对一：几个人可以共用一个会话，但许可名单、去重账本各自独立。
- 必修项：一条绑定只允许一个会话；同一个平台账号被两个绑定引用时，UI 直接标冲突，不静默取其一。
- 工作目录默认 `~/.dsh/pet-voice/bindings/<platform>-<account>/`，会话的 cwd 指过去；不把平台登录态写进仓库。

## 落在哪一层

- **插件（pocket-harness 内置辅助功能）**：绑定清单、开关、许可名单编辑、状态回读、额度、去重账本展示；检测到平台插件缺失时给安装入口（npm / 市场），不内置浏览器自动化。
- **宿主**：新增 `GET/POST /api/bindings`，与 `/api/goal`、`/api/inbox` 同级；绑定变更走宿主落盘，App 与桌面端看到同一份。
- **App**：设置里「平台绑定」一页，只读状态 + 开关 + 许可名单摘要；权限（通知、悬浮窗）仍在真正用到那一刻申请，不因为绑定账号就提前要。
- **会话内容**：分享进来的视频链接就是普通消息，走现有的 `/api/session`、`/api/poll`；App 不解析抖音链接，只渲染卡片。

## 风险与边界

- 平台条款、自动化频率、公开评论属于账号侧风险，默认全关、需要显式打开。
- 登录态只在浏览器 profile 里，不进 App、不进仓库、不进日志。
- 「看到了」不等于「喜欢」：兴趣只按播放进度和已确认互动算，这条沿用现有插件口径。
- 发送结果不明时不重发，保留收据回读核对——同样沿用现有口径。

## 下一步最小切片

1. `GET/POST /api/bindings` + 落盘 schema（先手工编辑 YAML 也能跑）。
2. 插件里一页绑定状态：账号、会话、许可数、今日额度、是否在线。
3. App「平台绑定」只读摘要 + 开关。
4. 与 `LockyBee/dsh-douyin-agent` 对接：绑定即它的许可名单来源，不另起一套。
